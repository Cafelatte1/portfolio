01. AI 학습용 부동산 데이터 파이프라인 구축 및 매출 전환

㈜코그콤 · 고객사 ㈜젠스타메이트

  • Python
  • Web Crawling
  • Browser Automation
  • REST API
  • Data Pipeline

Situation

  • 젠스타메이트 의뢰로 성북구청 건축 인허가 데이터를 AI 학습용으로 수집·공급하는 파이프라인을 맡았습니다.
  • 대상 사이트는 정적 페이지와 동적 페이지가 뒤섞인 구조였고, 수집한 데이터를 정제·표준화해 서비스에 공급하는 체계는 아예 없었습니다.

Task

  • 하나의 수집 방식으로는 전체 데이터를 가져올 수 없었습니다. 정적·동적 혼재 구조를 모두 커버하는 수집 방법이 필요했습니다.
  • 수작업 수집으로는 정기 갱신이 불가능했습니다. AI 모델이 바로 쓸 수 있는 형태로 정제해 주기적으로 공급하는 파이프라인까지 만들어야 했습니다.

Action

  • 페이지 유형을 먼저 분류했습니다. DOM 구조·네트워크 요청·렌더링 방식을 직접 분석해 어떤 페이지가 서버에서 완성되어 오고 어떤 페이지가 브라우저에서 그려지는지 구분했습니다.
  • 전면 브라우저 자동화를 쓰지 않았습니다. 모든 페이지를 브라우저로 여는 편이 구현은 쉽지만 속도와 리소스 비용이 큽니다. 정적 페이지는 HTTP 파싱으로, 동적 페이지만 브라우저 자동화로 처리하는 하이브리드 크롤링 모듈을 설계했습니다.
  • 수집 결과를 AI 학습에 적합한 표준 포맷으로 정제하고, 이를 API로 제공하는 서버까지 붙여 서비스가 바로 끌어다 쓸 수 있게 했습니다.

Pipeline

Result

  • 매출 전환

    구축한 파이프라인이 젠스타메이트 서비스의 핵심 인프라로 투입되어 실제 매출로 이어졌습니다.

  • 내부 솔루션 연동

    업무 자동화 솔루션 리컬럼과 연결되는 API 서버를 구축해 수집 데이터를 서비스에 직접 공급했습니다.

02. AI 에이전트 기반 이커머스 물품 구매 자동화 시스템 개발

개인 프로젝트 · FronyBrowser · FronyShopping

  • TypeScript
  • MCP
  • Playwright/CDP
  • HMAC
  • SQLite
  • DPAPI

Situation

  • "늘 사던 그 물 주문해줘"를 에이전트에게 맡기려면 로그인 비밀번호, 카드번호, 결제 PIN이 필요합니다. 그런데 그 값을 에이전트에게 주는 순간 LLM 컨텍스트·응답·로그에 전부 남습니다.
  • 더 근본적인 문제는 에이전트가 웹페이지에 의해 인젝션당할 수 있다는 점이었습니다. 화면에 적힌 가격과 수량을 그대로 믿고 결제하면, 조작된 페이지 하나로 잘못된 주문이 나갑니다.

Task

  • 에이전트가 개인정보 값을 단 한 번도 보지 않으면서 로그인부터 결제 완료까지 완주하게 만들 것.
  • 에이전트가 오염되더라도 피해가 한도 안에 묶이도록, 판단의 권한을 에이전트 밖에 둘 것.

Action

  • 값이 나가는 길을 하나로 좁혔습니다. 에이전트는 fill(ref, "{{vault:card.number}}")처럼 키 이름만 보냅니다. 실제 값으로 바뀌는 지점은 코드 전체에서 한 곳뿐이고, 치환된 값은 호출자에게 돌아가지 않고 브라우저로만 전달됩니다. 응답은 { filledFrom, len } — 키 이름과 길이만 남습니다.
  • 나가는 모든 응답을 한 출구에서 검사합니다. HTTP와 MCP 두 입구 중 한쪽에만 두면 다른 쪽이 우회하므로, 스크러버를 통과한 객체만 만들 수 있는 타입을 정의해 검사를 빠뜨린 코드는 아예 컴파일되지 않게 했습니다. 카드번호는 하이픈·마스킹·뒤 4자리 같은 표기 변형까지 함께 지웁니다.
  • 읽지 않음으로써 막았습니다. 페이지 구조를 넘길 때 input의 value는 어떤 경로로도 읽지 않습니다. 지우는 게 아니라 처음부터 가져오지 않는 방식입니다. 스크린샷은 스크러버가 청소할 수 없으므로, 결제 iframe 안쪽까지 내려가 입력 필드를 이미지 단계에서 마스킹합니다.
  • 임의 JS 실행을 넣지 않았습니다. 스크러버는 평문 일치로 동작하므로 btoa(value) 한 줄이면 방어 전체가 무력화됩니다. 그래서 편의 기능 대신 핸들러 폴더 자체를 기능 화이트리스트로 삼았습니다.
  • 판단과 실행을 두 서버로 분리했습니다. 가격·수량·한도 판정은 FronyShopping이 하고, 그 결과를 HMAC 서명된 결제 승인 토큰으로 넘깁니다. 토큰은 에이전트 손을 거쳐 전달되지만 서명·5분 만료·세션 바인딩·1회용 네 겹으로 막혀 있어, 인젝션당한 에이전트도 위조하거나 재사용할 수 없습니다.
  • 되돌릴 수 없는 지점을 기준으로 상태를 설계했습니다. 결제 직전에 승인을 기록하고 판정은 그 앞뒤에 남깁니다. 결제 중 상태는 만료시키지 않습니다 — 돈이 이미 나갔을 수 있으므로, 사람이나 에이전트가 결과를 확인해 닫을 때까지 남겨 둡니다.

개인정보 경계

에이전트(LLM)가 보는 것

fill(ref, "{{vault:card.number}}")
→ { ok: true, filledFrom: "card.number", len: 16 }

↓ 키 이름만 전달

FronyBrowser 프로세스 — 이 안에서만 값이 존재

암호화 vault → resolve() → CDP 키스트로크

↓ 실제 값

웹 페이지

입력 완료 · 응답은 스크러버를 거쳐 되돌아감

Result

20,595TypeScript 라인
29MCP 도구
536테스트 케이스
172스크러버 실제 적중

  • 실결제 완주

    컬리와 교보문고에서 로그인부터 결제·주문내역 확인까지 실제 결제로 완주했습니다. 보안 키패드를 통한 PIN 입력 경로까지 실측했습니다.

  • 설계가 작동한 증거

    감사 로그 1,183건 중 스크러버가 172건을 실제로 잡아냈습니다. 대부분 사이트가 배송지 이름·전화를 본문에 그려 넣은 경우였습니다.

03. 한국투자증권 이벤트 수집 모듈 개발 및 MCP 서버 구축

현업 실무자와 함께 진행한 협업 프로젝트 · project-kisevent

  • Python
  • MCP
  • VLM
  • FastAPI
  • SQLite
  • Pillow

Situation

  • 현업 실무자가 직접 겪던 불편에서 출발했습니다. "지금 영업점 고객 대상 이벤트가 뭐가 있지?"에 답하려면 공고를 하나씩 열어 눈으로 읽어야 했습니다. 어떤 정보가 실제로 필요한지, 대상 구분을 어떻게 나눠야 맞는지를 실무자와 함께 정의하며 진행했습니다.
  • 원인은 단순했습니다. 공고 내용이 전부 배너 이미지 안에 있고 HTML에는 텍스트가 없습니다. 배너는 세로 7,175~29,482px, 34건 합계 약 67MB였습니다.
  • 목록의 탭 구분(영업점 / 뱅키스)으로 대상을 가리는 방법도 틀렸습니다. 연금 이벤트가 양쪽 탭에 동시에 실려 오분류됐습니다.

Task

  • 이미지 안의 기간·대상·상품·실적 조건을 구조화해, 에이전트가 자연어 질문에 바로 답할 수 있게 만들 것.
  • 사내 개인 PC에서 도는 환경이므로 외부 API 키 없이 동작할 것.

Action

  • 처음 설계는 전문 전사였고, 그걸 버렸습니다. 배너를 여백 기준으로 11~20장 타일로 쪼개 전부 읽는 방식이었는데, 초기 34건에 40~50만 토큰이 들 것으로 추산됐습니다.
  • 버리기 전에 근거를 만들었습니다. 진행 중 공고 20건의 상단 4,000px를 전수 판독해, 필요한 정보 네 가지가 모두 y 1,400~3,450px 구간에 모여 있음을 확인했습니다. 그래서 고정 크롭 한 장 = 호출 한 번으로 줄이고, 전사 경로의 코드·테이블을 전부 삭제했습니다.
  • 별도 VLM API를 붙이지 않았습니다. MCP는 이미지를 그대로 모델에 전달할 수 있습니다. 크롭 이미지를 MCP 응답에 실어 사용자가 이미 쓰고 있는 에이전트의 비전 능력을 그대로 재사용했습니다. 별도 키도, 추가 비용도 없습니다.
  • 대상 판정 기준을 탭에서 이미지로 옮겼습니다. 배너 본문이 말하는 대상을 정본으로 삼아, 탭 구분이 만들어내던 편향을 없앴습니다.
  • 워크플로우를 문서가 아니라 프로토콜에 넣었습니다. "수집 1회 → 조회 → 미요약이면 먼저 요약 → 서브에이전트 병렬" 순서를 도구 설명문과 응답의 다음 지시에 박아 넣어, 에이전트가 읽는 것만으로 올바른 순서를 따르게 했습니다. 저장 시 스키마 검증에 실패하면 어느 필드가 왜 틀렸는지 돌려주고 에이전트가 고쳐 다시 보냅니다.

v1 — 전문 전사

배너 1장을 11~20 타일로 분할해 전부 읽기
초기 34건 기준 40~50만 토큰 추정

v2 — 고정 크롭

상단 정보 블록 1장만 크롭해 호출 1회
검출률 손실 없이 53건 전수 통과

Result

53/53정보 블록 검출
33/33진행 중 대상 판정
11탭 기준 오분류 교정
46테스트

  • 전수 검증

    진행 중 33건과 무작위 추출한 종료 20건, 총 53건 전부에서 크롭 범위를 벗어나 정보를 놓친 사례가 없었습니다.

  • 오분류 교정

    목록 탭 기준으로는 잘못 잡히던 11건을 이미지 판정이 바로잡았습니다. 전부 양쪽 탭에 걸쳐 있던 연금 이벤트였습니다.
